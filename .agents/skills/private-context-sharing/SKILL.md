# 非公開コンテキストの共有

最初に[共有方針と手順](../../../docs/private-sharing.md)、[導入手順](../../../docs/collaborator-setup.md)を読む。原資料はknowledge/AGENTS.mdとknowledge/SCHEMA.md、タスクの状態移動はwork/AGENTS.mdとwork/WORKFLOW.mdも読む。Git操作にはgit-workflowを併用する。

## 共有前

1. 公開KOKOと非公開KOKO-privateの絶対パス・Git root・remote・branch・差分を別々に確認する。Private表示を実際に確認できなければ、資料のpushを止める。公開remoteの上書きや、公開Gitへのforce addで代用しない。
2. 依頼が送信・受信・確認だけのどれか、対象メンバーと外部変更の許可を確認する。新規アカウントへの権限付与、共有先変更、資料中の第三者情報や権利制限が未解決なら、その部分だけ止めて質問する。
3. 公開追跡ファイルを除き、knowledge/raw、動的work、プロジェクト用memoryの新規・更新・移動・削除候補を確認する。将来追加された資料も候補に含めるが、フォルダー全体を無条件に転送しない。
4. 生成物、仮想環境、node_modules、キャッシュ、秘密、個人Codex履歴を除外する。work配下でも検証用ランタイムは資料ではない。秘密検出時は値を出力せず、パスと保留理由だけを報告する。

## 反映

1. 送信前に非公開mainの相手側更新を確認する。コピー元・先の相対パス、サイズ、SHA-256を比較し、違いがある場合は双方の未共有変更を調べる。内容を確認せず上書きしない。
2. 確定したファイルだけをcontext配下とKOKOの対応パスの間でコピーする。原資料を改変しない。解決した絶対パスが意図した範囲内か確認し、junction・symlinkを辿って範囲外へ出ない。タスクの移動・削除は個別に検証し、同一タスクの複数状態を残さない。再帰的なミラー削除を使わない。
3. コピー後のhash、公開側のignoreとindex、非公開側の差分を確認する。共有地点に対応する公開commitを非公開側へ記録する。対象リストや機微な差分をPublicのPRへ複製しない。
4. 許可された場合だけ、非公開側で目的別commitとPRを作る。mainへ通常の直接pushをしない。pushの不明確な結果はremoteを確認してから再試行する。merge、アクセス権の追加、相手PCでの操作を実施済みと推定しない。

## 引き渡し

送信対象、除外、衝突、hash確認、両リポジトリのcommit／PR、未反映の資料、受取側で必要な操作を記録する。引き渡し時に資料が増えていても、外部送信の許可がなければ差分の案内までとする。相手のPCを実際に確認していない限り「導入完了」としない。
