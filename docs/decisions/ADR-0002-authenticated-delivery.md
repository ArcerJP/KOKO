# ADR-0002: メディアの取得にも認証を必須にする

## 状態

Accepted（認証方針2026-09-21、契約一式の承認2026-09-22、iijima）。[第0日](../product/day-zero.md)に合意を記録。実装・実機性能・費用検証は第1〜第3要件です。

## 背景

原資料X-1/X-2/X-5/X-16は推測困難な公開URLとcacheを想定していました。外部共有先が未ログインでも閲覧できる点を確認したところ、ユーザーは「配信時も必ず認証する方式」を選択しました。

## 決定

- 原本・派生画像のR2バケットをどちらも非公開とする。公開用R2 URLは作らない。
- Streamは判定前後・clipとも`requireSignedURLs=true`を維持する。`allowedOrigins`だけを認証と見なさない。
- URL単体では再生権限を与えない。アプリの`/media/…`ゲートが画像・サムネイル・動画manifest・segment・鍵などの各要求でセッション/JWTを検証する。
- Stream署名はサーバー側からの取得にだけ使用する。署名済み上流URLをブラウザへ返したりredirectしたりしない。HLS中のすべての上流参照をゲートへ書き換える。
- ブラウザ/外側CDNには`private, no-store`。認証・公開可否の検査後に限って、派生物の版に基づくWorker内部cacheを利用する。原資料の公開URLとブラウザ向け1年immutableは置き換える。
- Cookieは同一origin・Secure・HttpOnly、state変更にはOrigin/CSRF検証。OAuthとセッション更新は第1要件で実装/検証する。
- 投稿非表示・BAN・キルスイッチをcacheより前に確認。URLを知られたこと自体で未ログイン者へデータを返さない。

## 代替案

推測困難な公開URLは不採用。短命なStream署名URLをブラウザへ返すだけの案も、共有された署名の有効期限内は利用可能なため今回の要望を満たしません。署名は上流アクセスに限定します。

## 影響と受入試験

毎回の認証/認可・proxy通信・HLS書換えにより、呼出し回数と費用が増えます。元資料の費用見積りと公開CDNキャッシュ試験はそのまま使いません。Range、HLSの子playlist/segment、Cookie伝搬、失効後再取得、iOS/Android再生、最大6本同時再生、内部cache hit、p95と費用をB1-8/B2-7/B3-8で測定します。

認証前のcache hit、上流URL漏れ、任意URL proxy（SSRF）、公開画像最適化経路、他イベント資産への取得を否定系で試験します。公開可否の確認に使うデータの鮮度を測り、通報後10秒以内の新規取得拒否を満たす必要があります。負荷を理由に認可cacheへ変える場合は失効時間とのトレードオフを再承認します。

ログイン済み利用者がすでに取得・保存したbytes、スクリーンショット、録画は回収できません。この方式はDRMではありません。

## 一次資料と設計上の推論

[Streamの公式仕様](https://developers.cloudflare.com/stream/viewing-videos/securing-your-stream/)では、署名トークンを動画IDの代わりにURLへ使用します。そのURLをブラウザへ渡すだけではログインセッションへの継続的な束縛にならない、という点からKOKO独自のゲート設計を導いています。ゲートがすでに提供・検証済みという意味ではありません。
